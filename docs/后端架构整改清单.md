# 后端架构整改清单

> 状态：进行中
> 建立日期：2026-08-08
> 适用范围：Cairn Go 后端

## 目的

当前后端已经形成可运行的模块化单体，并通过 `go test -race ./...`、`go vet ./...` 和 `golangci-lint run`。但部分设计来自 go-zero 风格，与更常见的 Go 显式依赖、强类型和 Context 使用方式存在差异。

项目仍处于较小规模，现在完成整改的成本最低。本清单只记录架构与代码组织问题，不记录普通业务 Bug。后续严格按照顺序一次解决一项，每项完成后更新状态和验证结果。

## 目标架构

```text
HTTP Request
  → Router / Middleware
  → Handler
      Request DTO、HTTP 边界、Cookie
  → Logic / Application Service
      业务规则、业务编排、强类型 Result
  → Repository Interface
  → PostgreSQL Repository
```

目标依赖方向：

```text
app（统一组装）
  ├── Handler → Logic + HTTP 辅助包
  ├── Logic   → 领域模型 + Repository 接口
  └── Repository → 领域模型 + pgx
```

核心原则：

1. Context 显式传递，不保存在长期对象中。
2. 构造函数只接收真正使用的依赖。
3. Logic 返回强类型 Result，不返回数据库模型和 `any`。
4. HTTP 状态映射集中处理，业务层不依赖 HTTP 细节。
5. Handler 保持简洁，但不为了隐藏简单解析而制造大量组合适配器。
6. 不引入当前业务不需要的企业级抽象。

## 整改顺序

### A01：Logic 不再保存 `context.Context`

- **优先级**：P0
- **状态**：已完成（2026-08-08）
- **当前情况**：`AuthLogic`、`PostLogic`、`CommentLogic`、`JSONLogic` 在结构体中保存请求 Context，并在每个请求中重新创建 Logic。
- **影响**：不符合 Go 官方 Context 使用建议；对象生命周期与单次请求绑定，阻碍 Logic 复用，也让依赖生命周期变得模糊。
- **目标**：Logic 构造函数不接收 Context；所有需要 Context 的方法都把 `ctx context.Context` 作为第一个参数。

目标形式：

```go
type PostLogic struct {
    repo blog.PostRepo
}

func (l *PostLogic) Get(ctx context.Context, slug string) (PostDetailResult, error)
```

- **验收标准**：
  - Logic 结构体中不存在 `context.Context` 字段。
  - Logic 方法显式接收 Context，并传给 Repository。
  - 全部测试、race、vet、lint 通过。
- **完成验证（2026-08-08）**：
  - 四个 Logic（Auth/Post/Comment/JSON）构造函数不再接收 Context；需要 Context 的方法全部改为 `ctx context.Context` 首参；JSONLogic 纯计算方法保持无 ctx。
  - 全部调用点（auth handler、auth middleware、post/comment handler、seo sitemap、tool handler、cmd/seed）已同步更新。
  - 验证结果：`go build`、`go test -count=1 ./...`、`go test -race -count=1 ./...`、`go vet ./...`、`golangci-lint run`（0 issues）、`git diff --check` 全部通过。
  - 静态搜索确认：Logic 结构体无 `context.Context` 字段、无 `l.ctx` 残留、无旧 `NewXxxLogic(ctx, ...)` 调用。

### A02：用精确构造函数注入替代业务层中的完整 `ServiceContext`

- **优先级**：P0
- **状态**：已完成（2026-08-08）
- **当前情况**：所有 Handler 和 Logic 都能访问完整 `ServiceContext`。
- **影响**：依赖不透明；随着 Redis、文件、AI 或第三方服务增加，`ServiceContext` 容易演变成 Service Locator 和“上帝对象”。
- **目标**：`app` 继续作为 Composition Root，但 Logic 只接收实际使用的 Repository 或服务；Handler 直接接收对应 Logic。

目标形式：

```go
postLogic := logic.NewPostLogic(postRepo, renderer)
postHandler := handler.NewPostHandler(postLogic)
```

- **验收标准**：
  - Logic 不导入 `internal/svc`。
  - Handler 不通过 `ServiceContext` 临时创建 Logic。
  - 构造函数参数可以直接说明真实依赖。
- **完成验证（2026-08-08）**：
  - `AuthLogic` 接收 `auth.UserRepo`、`auth.SessionRepo`；`PostLogic` 接收 `blog.PostRepo`；`CommentLogic` 接收 `blog.PostRepo`、`blog.CommentRepo`；`JSONLogic` 无依赖。
  - Handler 直接保存对应 Logic：`AuthHandler` 保存 `*logic.AuthLogic`，`PostHandler`/`CommentHandler`/SEO/工具 Handler 同理；`LoadUser` 中间件直接复用 AuthLogic。
  - `internal/svc` 在全部调用点改造后无任何引用，已删除（`internal/svc/serviceContext.go`）。
  - 静态搜索确认：Logic/Handler/Middleware 均无 `internal/svc`、`ServiceContext`、`svcCtx` 引用。

### A03：统一依赖生命周期，消除每请求重复初始化

- **优先级**：P0
- **状态**：已完成（2026-08-08）
- **当前情况**：`NewPostLogic` 每次请求都会创建 Goldmark、Chroma 和 Bluemonday Policy；无状态的 `JSONLogic` 也被迫保存无用依赖。
- **影响**：重复初始化；所有 Logic 被强制套用同一种模板；未来新增依赖时更难判断应当按请求创建还是全局复用。
- **目标**：Repository、Logic 和初始化后只读的渲染组件在应用启动时创建一次；请求状态仅通过 Context 和方法参数传递。无状态功能不保留伪依赖。
- **验收标准**：
  - Markdown 渲染器和安全策略不再每请求创建。
  - `JSONLogic` 不保存未使用的 Context 或 ServiceContext。
  - 代码中不存在为了模板统一而添加的 `_ = value` 或 `reserved` 参数。
- **完成验证（2026-08-08）**：
  - `app` 成为 HTTP 服务的 Composition Root：Repository → Logic → Handler 均在启动时组装一次，请求过程不再创建 Logic；`cmd/seed` 作为独立命令，只组装自身所需依赖。
  - Goldmark/Chroma/Bluemonday 在 `NewPostLogic`/`NewCommentLogic` 中只初始化一次。并发复用依据：Bluemonday v1.0.27 README 明确“Policy creation/editing is not safe to use in multiple goroutines / the policy … is safe to use the policy in multiple goroutines”；Goldmark v1.8.2 源码中 `parser.Parse` 用 `sync.Once`（`initSync`）惰性初始化，`Convert` 每次调用新建 Reader 与 AST、不改接收者。
  - `JSONLogic` 变为无依赖的空结构体（`NewJSONLogic()`）。
  - 删除 `PostLogic.Create` 的伪参数 `user`（路由已由 `RequireRole(admin)` 鉴权）及 `_ = user // reserved`；同步更新 handler 与 `cmd/seed` 调用点。`CommentLogic` 中用于权限判断的用户参数保留。
  - 未使用全局变量或互斥锁实现复用。

### A04：Logic 返回强类型 Result，移除 `any`

- **优先级**：P0
- **状态**：已完成（2026-08-08）
- **当前情况**：面向 API 的 Logic 方法统一返回 `(any, util.Code, string)`。
- **影响**：失去编译期类型检查；调用方可能需要类型断言；重构字段时编译器无法覆盖完整调用链。
- **目标**：每个用例返回明确类型，例如 `PostDetailResult`、`PostListResult`、`CommentResult`。删除类业务使用无数据结果。

最终形式：

```go
func (l *PostLogic) Get(ctx context.Context, slug string) (PostDetailResult, util.Code, error)
```

- **验收标准**：
  - 面向 Handler 的 Logic 方法不返回 `any`。
  - Handler 中不存在业务结果类型断言。
  - Result 字段变更能够触发编译错误而不是运行时错误。
- **完成验证（2026-08-08）**：
  - Post、Comment、Auth 和 Tool 的面向 Handler 方法全部返回具体 Result；JSON 格式化新增 `FormatJSONResult`。
  - 删除、登出、注册等不需要向直接调用方返回数据的操作不再伪造 `any` 结果。
  - Handler 直接使用编译期已知的 Result，认证 Handler 中的 `data.(*logic.LoginResult)` 类型断言已删除。

### A05：用统一 AppError 替代消息字符串并保留错误原因

- **优先级**：P1
- **状态**：已完成（2026-08-08）
- **当前情况**：Logic 直接返回 `(data any, util.Code, string)`，成功数据、错误类别和对外消息混在同一个三元返回值中。
- **影响**：调用方必须同时判断 Code、处理字符串消息并断言结果类型；原始内部错误无法保留，未知错误也缺少统一兜底。
- **目标**：在 `internal/util/response.go` 中定义统一 `AppError`，同时保留对外消息和原始错误；Logic 返回统一管理的 `util.Code` 与 `error`，由 `util.Reply` 识别 `AppError` 并集中完成 HTTP 状态和 JSON 响应映射。

设计取舍：

- Cairn 当前规模较小，`AppError`、业务码和 HTTP 映射统一放在 `response.go`，不为错误模型单独增加 package。
- Logic 继续返回集中定义的 `util.Code`，确保成功码和错误码使用同一套定义；消息字符串改为 `error`。
- 这是简化代码组织的主动取舍；A07 收紧 `util`、`httpx` 包职责时，再结合实际调用方决定是否拆分错误模型。

目标形式：

```go
data, code, err := h.postLogic.Get(r.Context(), slug)
util.Reply(r.Context(), w, data, code, err)
```

- **验收标准**：
  - Logic 返回 `error`，不再返回裸消息字符串。
  - 已知错误具有稳定的机器码和对外消息。
  - 未知内部错误统一映射为 500，同时保留可记录的原始错误。
  - Handler 仍保持简短，不重复编写状态映射。
- **完成验证（2026-08-08）**：
  - `AppError` 保存客户端安全 Message，并通过 `Unwrap()` 保留原始 Cause；统一使用 `NewAppError(message, cause)` 创建，无底层原因时传入 `nil`。
  - `util.Reply` 对外仍只有一个函数；已知 `AppError` 使用 Logic 返回的统一 Code 和安全消息，未知普通错误强制映射为 `CodeInternalError` 与 `internal server error`。
  - Request 适配器与认证 Middleware 只做新签名的机械适配，没有改变 A06 所涉及的解析结构、鉴权顺序或响应契约。
  - 响应测试覆盖 AppError Cause、内部消息隔离和未知错误 500 兜底。
  - 验证结果：`go build ./...`、`go test -count=1 ./...`、`go test -race -count=1 ./...`、`go vet ./...`、`golangci-lint run`（0 issues）、`git diff --check` 全部通过。

### A06：重新设计请求解析，避免适配器组合爆炸

- **优先级**：P1
- **状态**：待处理
- **当前情况**：已有 `ParseBody`、`ParsePath`、`ParsePathAndBody`、`ParsePositiveInt64Path`、`ParsePagination`。
- **影响**：接口组合增多后，容易继续出现 `ParsePathAndQuery`、`ParsePathAndQueryAndBody` 等大量高阶函数。
- **目标**：保留少量稳定的通用能力，不为每种参数组合增加新函数。明确 Handler 可以承担哪些简单 HTTP 边界处理，哪些必须由公共解析器处理。
- **验收标准**：
  - 新接口组合不需要新增成对或三合一解析函数。
  - Body 大小限制、未知字段和 Validate 仍由统一入口处理。
  - Path、Query、Body 的错误响应格式一致。

### A07：收紧 `util`、`web` 的包职责

- **优先级**：P1
- **状态**：待处理
- **当前情况**：`util` 保存请求与响应，`web` 保存安全中间件、限流和站点 URL；两者都是宽泛名称。
- **影响**：后续通用代码容易无规则地进入 `util` 或 `web`，最终形成大杂烩。
- **目标**：使用按职责命名的包。候选方案：

```text
internal/httpx/          请求绑定、统一响应
internal/middleware/     安全、限流、认证中间件
```

站点 URL 归入配置或 SEO，不进入 HTTP 通用工具。

- **验收标准**：
  - 每个公共包可以用一句话清晰说明职责。
  - 业务无关工具不会继续集中到一个 `util` 包。
  - 不产生循环依赖。

### A08：完成领域模型、认证 Principal 与 API Result 的边界

- **优先级**：P1
- **状态**：待处理
- **当前情况**：博客 Result 已经在 Logic 组装，但 `blog.Post`、`blog.Comment`、`auth.User` 等内部模型仍带有 JSON 标签；认证接口仍可能直接使用 `auth.User`。
- **影响**：数据库模型、认证上下文和对外 API 模型的边界不完全一致；内部字段变化可能影响接口契约。
- **目标**：
  - Repository 使用领域/持久化模型。
  - 认证 Context 保存最小 `Principal`，例如 ID、Username、Role。
  - API 输出统一使用 `XxxResult`。
  - 内部模型不承担 JSON 接口契约。
- **验收标准**：
  - Handler 不直接响应 `auth.User`、`blog.Post` 或 `blog.Comment`。
  - 对外字段只能在 Result 中声明。
  - 密码、Token 和内部状态不会因为模型新增字段而被自动公开。

### A09：补齐应用级日志与公共依赖设计

- **优先级**：P2
- **状态**：待处理
- **当前情况**：`app.New` 接收 logger 但没有使用；`util.Reply` 接收 Context 但没有使用；请求日志仍使用 chi 默认 Logger。
- **影响**：依赖签名与真实用途不一致；后续请求 ID、结构化日志、错误追踪难以形成统一入口。
- **目标**：要么删除未使用的参数，要么真正建立基于 `slog` 的请求日志和错误日志依赖；不保留“以后可能会用”的伪参数。
- **验收标准**：
  - 构造函数参数全部被真实使用。
  - 请求日志能够关联 Request ID。
  - 内部错误可记录，HTTP 响应不泄露内部细节。

### A10：建立分层测试策略

- **优先级**：P1，随前述整改同步推进
- **状态**：待处理
- **当前情况**：测试主要集中在 Handler、Middleware 和 HTTP 工具，Logic 独立测试和 Repository 集成测试不足。
- **影响**：业务规则只能通过 HTTP 间接测试；SQL 扫描、约束和事务缺乏真实数据库验证。
- **目标**：

```text
Handler 测试       参数、鉴权、HTTP 状态、响应契约
Logic 单元测试     业务规则、权限、状态转换
Repository 集成测试 SQL、约束、扫描、事务
```

- **验收标准**：
  - 每个新增业务规则首先有 Logic 测试。
  - 关键 Repository 查询有 PostgreSQL 集成测试。
  - Handler 测试不重复覆盖 Logic 的全部分支。

### A11：制定 Handler 文件增长规则

- **优先级**：P2
- **状态**：待处理
- **当前情况**：DTO、Validate 和接口方法紧挨放置是正确的，但一个资源的所有接口长期集中在同一文件会不断增长。
- **影响**：文章增加更新、删除、草稿、发布、标签和搜索后，`postHandler.go` 会成为大文件。
- **目标**：保持同包和相邻原则，但按接口拆文件：

```text
blog/handler/
  postRoutes.go
  postCreate.go
  postGet.go
  postList.go
  postUpdate.go
  postDelete.go
```

- **验收标准**：
  - Request DTO、Validate、Handler 方法仍在同一文件且相邻。
  - 路由声明集中可读。
  - 不因为文件拆分创建额外抽象层。

## 明确暂不引入

以下设计在当前规模下没有足够收益，暂不加入：

- 微服务拆分
- CQRS 框架
- Unit of Work 抽象
- 通用 BaseRepository
- 事件总线
- 全局 DTO 包
- 为每个结构体创建接口
- Redis、消息队列和 Elasticsearch

只有出现真实业务需求时，才通过新的架构决策记录引入。

```bash
gofmt -w <修改文件>

```

同时检查：

1. API 路径、状态码和 JSON 字段没有无意变化。
2. 没有把现有未提交改动覆盖或回滚。
3. `AGENTS.md` 与实际架构保持一致。
4. 每一处修改都能追溯到当前正在处理的清单项。
