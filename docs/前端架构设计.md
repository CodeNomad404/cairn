# Cairn 前端架构设计

## 1. 目标

前端采用 Vue 3 单页应用（SPA），负责页面渲染、路由和用户交互；Go 后端只提供 `/api/v1` JSON 接口、健康检查和 SEO 文件。

```text
浏览器
  ↓
Vue SPA（页面、路由、交互）
  ↓ /api/v1
Go 后端（Handler → Service → Repository → PostgreSQL）
```

开发时，Vite 将 `/api` 代理至本地或测试后端。生产环境由 Caddy 提供 Vue 构建产物，并将 `/api/` 转发至 Go。

## 2. 技术选择

| 类别 | 选择 | 原因 |
| --- | --- | --- |
| 框架 | Vue 3 + Vite | 现有工程已使用，Vite 是 Vue 官方推荐工具链。 |
| 语言 | TypeScript | 在项目规模仍小的时候建立接口与组件类型边界。 |
| 路由 | Vue Router | Vue 官方 SPA 路由方案。 |
| 全局状态 | Pinia | 仅保存跨页面状态，例如当前登录用户。 |
| 请求 | 原生 `fetch` | 项目需求简单，不额外引入 Axios。 |
| 单元/组件测试 | Vitest + Vue Test Utils | 与 Vite 共用配置和编译链。 |
| E2E 测试 | Playwright（后续） | 测试环境验证登录、发文、评论等关键流程。 |
| 代码质量 | ESLint + Prettier + vue-tsc | 保证提交前的静态检查、格式与类型检查。 |

参考：[Vue 工具链](https://vuejs.org/guide/scaling-up/tooling)、[Vue Router](https://router.vuejs.org/guide/)、[Vue 测试](https://vuejs.org/guide/scaling-up/testing)。

## 3. 目录职责与依赖方向

前端按业务模块组织，目录表达代码归属，不要求前端模块与后端 package 一一对应。

```text
web/
├── public/                  # 保留固定 URL 的公开资源
└── src/
    ├── main.ts              # 启动入口
    ├── assets/              # 由 Vite 导入和构建的资源
    ├── app/                 # 应用装配、路由、Layout 和全局初始化
    ├── modules/             # 按业务能力内聚的模块
    │   └── <module>/
    │       ├── index.ts     # 模块对外入口
    │       ├── api/
    │       ├── views/
    │       ├── components/
    │       ├── composables/
    │       ├── store.ts
    │       └── types.ts
    └── shared/              # 不理解具体业务的基础能力
```

子目录和文件按需创建，不为补齐结构而增加空文件。代码归属由语义决定，不由引用次数决定；具有业务含义的代码即使被多个模块使用，仍留在所属业务模块。

依赖规则：

- `main.ts` 只启动应用。
- `app` 可以依赖 `modules` 和 `shared`；`modules` 不得依赖 `app`。
- 业务模块之间允许单向依赖，但不得形成循环依赖。
- `shared` 不得依赖 `app` 或任何业务模块。
- 模块外部代码（包括 `app` 和其他业务模块）只能从目标模块的根 `index.ts` 导入。
- 禁止模块外部代码直接依赖该模块的 `api`、`views`、`components`、`composables`、`store.ts`、`types.ts` 或其他内部文件。
- 模块内部直接导入自身文件，不经过自己的 `index.ts`。
- `index.ts` 只使用显式导出，禁止 `export *`。
- `app/router` 直接动态导入模块 `views` 是唯一例外，用于保留路由级懒加载。
- 禁止用 `common`、`helpers`、`misc` 等模糊目录收纳无法归类的代码。

## 4. 页面数据流与基础设施边界

```text
Router → View → Component
           ├→ Module API
           └→ Composable → Module API

Router / View → Store → Module API
Module API → Shared HTTP → Go API
```

- Router 负责路由、Layout、Meta 和导航级守卫；守卫可读取 Store，不调用具体业务 API。
- View 负责读取路由、页面装配、页面专用状态和导航。简单请求可直接调用同模块 Module API，不强制创建 Composable。
- Component 负责界面和局部交互；需要独立异步状态时使用同模块 Composable，不直接调用 Module API 或 Shared HTTP。
- Composable 负责有状态逻辑。涉及异步 `data/loading/error`、Vue 生命周期、请求竞态、多个操作共享状态或复用需求时，应从 View/Component 提取。
- Store 只管理跨页面或跨生命周期的共享状态，可调用 Module API，不作为默认页面缓存。
- Module API 定义业务接口路径、方法、参数和返回类型，只通过 Shared HTTP 发起请求，不操作 Router、Store 或 UI。
- Shared HTTP 只负责通用 `fetch`、序列化、响应解析和传输错误，不包含业务路径、导航或提示。
- Utility 是不依赖 Vue 生命周期的纯函数，不是必须经过的调用层。

View 允许保留少量只服务当前模板的 `ref`、`computed`、页面导航和事件转发。不得为了让 View 只剩模板，机械创建一对一的 Page Composable。API、类型、跨页面状态和纯函数分别归属 `api`、`types.ts`、`store.ts` 和明确命名的纯逻辑文件，不统一塞入 `composables`。

## 5. 组件与逻辑复用

项目统一使用 Vue 3 Composition API 和 `<script setup lang="ts">`。

- View 是 Router 直接加载的完整页面，负责路由交互和组装业务组件，不作为普通子组件复用。
- Layout 属于 `app`，只组装应用级骨架、导航和 `RouterView`，不包含具体模块业务。
- `app/components` 可理解整个 Cairn 应用，并通过模块根 `index.ts` 使用 Router 或业务 Store。
- 业务组件属于所在模块，可使用本模块类型和 Composable；数据优先通过 Props 输入，用户意图通过 Events 输出。
- Shared 组件不理解业务，不导入 Router、业务 Store 或业务类型，只通过 Props、Events、Slots 和 `v-model` 协作。

组件通信规则：

- 禁止修改普通 Prop，禁止通过父子组件实例读写普通业务状态。
- `v-model` 是显式双向契约；子组件只因直接用户输入更新模型，由其他状态引起的预填、重置和切换由状态持有者负责。
- 禁止用模板 Ref 或 `defineExpose` 控制普通表单和业务状态；仅聚焦、滚动、媒体、Canvas 等命令式 UI 能力可作为例外。
- `provide/inject` 不用于普通父子通信；仅用于真正跨越深层组件树的稳定上下文，并使用强类型 `InjectionKey`。

只在存在独立职责、稳定组件接口、递归渲染、实际复用或独立测试边界时拆分组件。不按文件行数拆分，不为无语义包装、少量重复或假设的未来复用创建组件。

Composable 使用 `useXxx` 命名，接收普通值、Ref 或 getter，返回明确命名的状态和操作。它必须在失效或卸载时清理请求、监听器和其他副作用。不依赖 Vue 的逻辑保持为纯函数；简单且只在一处使用时可留在原文件，复杂、需测试或确实复用时再提取。

## 6. TypeScript 类型契约

保持 `strict` 类型检查，禁止显式 `any`、`@ts-ignore` 以及用宽泛断言掩盖建模问题。

- API JSON Body 命名为 `XxxRequest`，成功响应 `data` 命名为 `XxxResult`，与真实后端契约保持一致。
- 模块级 API 契约、多文件使用的稳定类型和需对外公开的类型放在模块 `types.ts`；Props、Composable 状态和辅助联合类型默认就近定义。
- 不同时建立内容相同的 DTO、Entity、Model 和 ViewModel；只有真正发生数据转换时才增加展示类型。
- Catch、`JSON.parse`、浏览器存储、第三方输入和网络原始数据使用 `unknown`，必须收窄后使用。
- 优先使用类型守卫和 `satisfies`；`as` 只用于前置检查已证明安全的边界、`as const` 字面量或 Shared HTTP 的单一传输边界。禁止双重断言。
- `request<T>` 是编译期契约，不代表对 `T` 做了运行时验证；Shared HTTP 必须先验证通用响应信封，业务代码不得再将未知响应断言为 Result。
- 字段必定存在但可为空时使用 `T | null`，可能不存在时使用 `?`，空集合使用 `[]` 而非 `null`。
- API 日期时间保持 ISO 8601 `string`，JSON 数字 ID 使用 `number`，固定枚举值使用字符串联合而非 TypeScript `enum`。
- 泛型只用于表达真实的输入输出关系，不为单一调用方创建通用类型体系。
- 纯类型导入使用 `import type`；模块内部从就近文件导入，模块外部仍只能从根 `index.ts` 导入。

## 7. 路由设计

| 路径 | 页面 | 权限 |
| --- | --- | --- |
| `/` | 首页 | 公开 |
| `/posts` | 文章列表 | 公开 |
| `/posts/:slug` | 文章详情与评论 | 公开 |
| `/login` | 登录 | 未登录用户 |
| `/register` | 注册 | 未登录用户 |
| `/admin/posts/new` | 发布文章 | admin |
| `/tools/json` | JSON 格式化 | 公开 |
| `/tools/diff` | 文本对比 | 公开 |

路由守卫只负责页面访问控制：访问管理员页面前请求或读取当前用户状态；真正的权限判断仍由 Go 后端执行。

生产环境必须配置 SPA 回退：访问 `/posts/slug` 时，Caddy 返回 `index.html`，再由 Vue Router 渲染对应页面；`/api/` 例外，必须转发给 Go。

## 8. API 调用规范

接口定义以仓库根目录的 [`api/openapi.yaml`](../api/openapi.yaml) 为准。

```text
modules/blog/api/posts.ts
  → shared/api/http.ts
  → /api/v1/posts
  → Go blog/handler/postHandler.go
```

`shared/api/http.ts` 统一完成：

- 设置 `Accept: application/json`。
- 解析成功响应和 `{ "error": { "code", "message" } }` 错误响应。
- 保留 Cookie 会话；请求地址始终使用相对路径 `/api/v1/...`。
- 不在请求层自动跳转页面；401 由路由守卫或页面按场景处理。

各模块只导出语义化函数，例如：

```ts
listPosts(page, pageSize)
getPost(slug)
createComment(slug, input)
login(credentials)
```

## 9. 状态管理

Pinia 只建立 `auth` Store：

```text
user       当前用户，未登录为 null
loading    初始化登录状态时为 true
fetchMe()  请求 GET /api/v1/auth/me
logout()   请求 POST /api/v1/auth/logout 并清空 user
```

文章列表、评论列表等服务端数据，第一阶段放在对应 View 或 composable 中；只有确实被多个页面共享、且需要缓存时，才建立模块 Store。

## 10. 页面实现顺序

1. 建立 TypeScript、Vue Router、Pinia、ESLint、Prettier、Vitest 骨架。
2. 建立全局布局、导航和 404 页面。
3. 实现文章列表与文章详情，调用已存在的文章接口。
4. 实现登录、注册、当前用户状态和路由守卫。
5. 实现评论列表、发布与删除。
6. 实现管理员文章发布。
7. 迁移 JSON 工具与文本对比工具。

每完成一个模块，在测试后端联调；不等待所有页面完成才验证。

## 11. 质量门禁

前端每次合并前至少通过：

```text
pnpm lint
pnpm typecheck
pnpm test
pnpm build
```

测试策略：

- 纯函数、`composable`：Vitest 单元测试。
- 关键组件：Vue Test Utils 组件测试。
- 登录、评论、管理员发文：后续使用 Playwright 在测试环境跑端到端测试。

Vue 官方建议尽早开始测试；Vitest 可直接复用 Vite 配置，适合本项目。

## 12. 明确不做

- 不引入 Vuex、Axios、Element Plus、微前端。
- 不将所有业务状态塞进 Pinia。
- 不保留 Go 模板和 HTMX 双实现。
- 不让前端绕过后端直接访问 PostgreSQL 或测试数据库。
- 不在未稳定前自动生成复杂 API Client。

## 13. 完成标准

- Vue 构建产物可由 Caddy 提供。
- 所有页面只通过 `/api/v1` 与 Go 后端通信。
- 浏览器直接打开任意前端路由不会 404。
- 未登录与非管理员操作在前后端都有正确反馈。
- 前端接口调用与 `api/openapi.yaml` 一致。
